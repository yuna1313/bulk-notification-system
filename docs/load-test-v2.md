# v2 부하 테스트 결과

Kafka 기반 비동기 구조(v2)가 v1의 한계를 얼마나 해소했는지를 같은 조건에서 측정한 기록입니다.
[v1 문서](load-test-v1.md) 마지막의 "v2 개선 목표" 표에 답하는 것이 이 문서의 목적입니다.

## 요약

- **처리량이 4.4건/초에서 30건/초가 됐습니다.** 10만 건 발송이 6시간 19분에서 **55분 29초**로 줄었습니다.
  그리고 v1과 마찬가지로 규모가 커져도 처리량이 흔들리지 않습니다.
- **발송이 다른 요청을 막지 않습니다.** 발송이 도는 동안 접수 API의 p(95)가 **56.99초에서 644ms**가 됐습니다.
- **처리량을 파라미터로 조절할 수 있습니다.** 파티션 수를 5·10·20으로 바꾸자 16.6·31.1·54.0건/초로
  거의 비례해 증가했습니다. v1에서는 무엇을 바꿔도 4.4건/초였습니다.
- **실패가 유실되지 않습니다.** 발송사 실패율 3%를 상대로 최종 실패율 **0.0016%**를 기록했습니다.

다만 **처리량 목표(44건/초)와 접수 API 응답 목표(100ms)는 파티션 10 기준으로 달성하지 못했습니다.**
그리고 **접수 API 자체는 v1보다 2.5배 느려졌습니다.** 두 가지 모두 본문에서 다룹니다.

## 이 문서를 읽기 위한 배경

### v1은 왜 느렸나

v1은 발송 요청 하나가 들어오면 **수신자를 한 명씩 순서대로** 처리했습니다.

```
발송 API ─→ 수신자1 발송(200ms) ─→ 수신자2 발송(200ms) ─→ ... ─→ 수신자 10만(200ms)
                                                                        ↑
                                                      여기까지 API가 응답을 안 함
```

발송사가 한 건에 200ms를 쓰니 10만 건이면 200ms × 100,000 = 약 5.5시간입니다.
실측 6시간 19분이 이 계산과 맞습니다.

문제는 두 가지였습니다.

1. **아무리 기다려도 6시간이다.** 순서대로 하나씩 하는 구조라 빨라질 방법이 없습니다.
2. **그동안 서비스 전체가 막힌다.** 발송 하나가 웹 서버 스레드 하나를 6시간 동안 붙잡습니다.
   동시 발송이 200건이면 스레드 200개가 전부 묶여서 다른 요청은 응답조차 못 받습니다.

### v2는 무엇을 바꿨나

**"발송한다"와 "발송을 지시한다"를 분리**했습니다.

```
발송 API ─→ "10만 건 보내라"는 지시를 적어두고 즉시 응답
                    │
                    ↓
              [ Kafka ]  ← 지시가 쌓이는 곳
                    │
        ┌───────────┼───────────┐
        ↓           ↓           ↓
     worker1       worker2   ...  worker10   ← 10개가 동시에 발송
```

API는 지시만 적고 빠집니다. 실제 발송은 별도 프로그램(**worker**)이 가져가서 처리합니다.
worker를 10개 돌리면 10건이 동시에 나가므로 이론상 10배 빨라집니다.

### Kafka 용어 최소한만

| 용어                  | 뜻                                                                                                                  |
| --------------------- | ------------------------------------------------------------------------------------------------------------------- |
| **토픽(topic)**       | 메시지가 쌓이는 통. 이 프로젝트에서는 `notification.send` 하나                                                      |
| **파티션(partition)** | 토픽을 나눈 칸. **동시에 처리할 수 있는 최대 개수를 결정합니다.** 파티션이 10개면 worker가 20개여도 10개만 일합니다 |
| **컨슈머(consumer)**  | 메시지를 꺼내 가는 쪽. 여기서는 worker                                                                              |
| **컨슈머 그룹**       | 같은 그룹에 속한 컨슈머끼리 파티션을 나눠 갖습니다. 그래야 중복 없이 나눠서 처리합니다                              |
| **오프셋(offset)**    | "어디까지 읽었는지"를 기록한 번호. worker가 죽었다 살아나도 이 번호부터 이어서 읽습니다                             |
| **lag(랙)**           | 쌓인 양 − 읽은 양. **얼마나 밀렸는지**를 나타냅니다                                                                 |
| **DLQ**               | Dead Letter Queue. 재시도를 다 써도 실패한 메시지를 따로 모아두는 통                                                |

**파티션이 왜 중요한지**가 이 문서의 핵심입니다. 파티션 수가 동시 처리 개수의 상한이고,
동시 처리 개수가 처리량을 결정합니다. 측정 E가 이것을 숫자로 확인합니다.

## 서비스 흐름과 테이블

측정 결과를 읽으려면 어느 단계에서 무슨 일이 일어나는지 알아야 합니다.

### 테이블 네 개

| 테이블                 | 무엇이 들어가나                                           | 누가 쓰나                                           |
| ---------------------- | --------------------------------------------------------- | --------------------------------------------------- |
| `notification`         | 발송 요청 1건 (제목·내용·채널·상태)                       | notification-api만                                  |
| `notification_message` | **수신자별 발송 건.** 10만 명이면 10만 행                 | notification-api가 만들고, **worker가 결과를 기록** |
| `outbox_event`         | Kafka로 보낼 발송 지시를 **보내기 전에 미리 적어두는 곳** | notification-api만                                  |
| `processed_event`      | worker가 **이미 처리한 지시**의 기록                      | worker만                                            |

두 애플리케이션이 같은 DB를 보지만, **양쪽이 함께 건드리는 테이블은 `notification_message` 하나뿐**입니다.
notification-api가 행을 만들고 worker는 발송 결과 컬럼만 갱신합니다.

### 발송 한 건이 흘러가는 순서

**1단계 — 접수** `POST /api/test/notifications`

```
notification            1행 생성 (PENDING)
notification_message    10만 행 생성 (전부 PENDING)
```

아직 아무것도 발송되지 않았습니다. "누구에게 무엇을 보낼지" 목록만 만든 상태입니다.

**2단계 — 발송 실행** `POST /api/notifications/{id}/dispatch`

```
notification            PENDING → DISPATCHING
outbox_event            10만 행 생성 (전부 PENDING)
                        ↓
                    202 응답
```

여기서도 발송은 안 됩니다. **"이 10만 건을 보내라"는 지시를 DB에 적기만 하고 응답합니다.**
v1이 이 시점에 6시간을 붙잡고 있었던 것과 대비됩니다.

> **왜 Kafka에 바로 안 보내고 DB(`outbox_event`)에 먼저 적을까요?**
>
> DB 저장과 Kafka 발행을 하나의 트랜잭션으로 묶을 수 없기 때문입니다.
> 순서를 어떻게 잡아도 한쪽만 성공하고 죽는 순간이 생깁니다.
> Kafka에 먼저 보내면 DB에 없는 발송이 나갈 수 있고, DB에 먼저 쓰면 발송 지시가 사라질 수 있습니다.
>
> 그래서 **DB에 먼저 적고, 나중에 별도로 발행**합니다.
> 발행에 실패하면 `PENDING`으로 남아 있으니 다시 시도하면 되어서 유실이 없습니다.
> 이 방식을 **Transactional Outbox 패턴**이라고 합니다.

**3단계 — poller가 Kafka로 발행** (1초마다 자동)

```
outbox_event의 PENDING을 500건씩 읽음
    → Kafka 토픽에 발행
    → PUBLISHED로 변경
```

**4단계 — worker가 발송** (Kafka에 메시지가 있는 즉시)

```
Kafka에서 지시를 꺼냄
    → processed_event에 INSERT 시도
        ├─ 성공 → 처음 보는 지시. 계속 진행
        └─ 중복 오류 → 이미 처리함. 건너뜀
    → 발송사(mock-provider) 호출
    → notification_message를 SUCCESS 또는 FAIL로 변경
```

> **`processed_event`는 왜 필요할까요?**
>
> 3단계의 poller는 "Kafka에 발행했다"고 표시하기 직전에 죽을 수 있습니다. 그러면 재시작 후
> 같은 지시를 또 발행합니다. Kafka 자체도 상황에 따라 같은 메시지를 다시 전달합니다.
> 이것을 **at-least-once(최소 한 번)** 전달이라고 합니다. 유실은 없지만 중복은 있습니다.
>
> 중복 발송은 사용자에게 문자가 두 번 가는 사고입니다. 그래서 worker가 처리한 지시의 ID를
> 기본키로 저장해두고, INSERT가 중복 오류를 내면 이미 처리한 것으로 판단해 건너뜁니다.

**5단계 — 완료 판정** (2초마다 자동)

```
DISPATCHING 상태이면서 PENDING인 메시지가 하나도 없는 요청을 찾아
    → COMPLETED로 변경
    → 완료 시각은 마지막 발송 시각(max(sent_at))으로 기록
```

완료 시각을 판정 시점이 아니라 **마지막 발송 시각**으로 잡는 이유는, 2초 주기의 판정 지연이
소요시간 측정에 섞이지 않게 하기 위해서입니다.

### 실패하면

발송사가 실패로 응답하면 worker가 예외를 던지고, Kafka가 같은 메시지를 다시 전달합니다.
**1초 간격으로 2번 더 시도**하고, 그래도 실패하면 `notification.send.dlq` 토픽으로 보냅니다.
v1에는 재시도가 없어서 실패가 그대로 유실됐습니다.

### v1과 달라진 조건

비교의 공정성을 위해 밝혀둡니다.

- **Kafka 브로커(Docker)가 같은 장비에서 추가로 동작합니다.** v1 측정 때는 없던 프로세스입니다.
  이 자원 경합이 측정값에 포함돼 있습니다.
- **API에 `-Dhttp.maxConnections=300`을 붙이지 않았습니다.** v1에서 이 옵션이 필요했던 이유는
  API가 직접 발송사를 호출했기 때문인데, v2는 worker가 호출하므로 API에는 불필요합니다.
- worker가 추가되어 JVM이 하나 더 떠 있습니다.

### 로그 설정에 대한 단서

**측정 A·B·C·E·F는 `loadtest` 프로파일 없이 측정했습니다.** 즉 SQL 로그가 켜진 상태였습니다.
측정 도중 발견해서 A의 10,000건 회차를 프로파일 적용 후 재측정해 영향을 확인했습니다.

|                          | 로그 켬    | 로그 끔    | 차이      |
| ------------------------ | ---------- | ---------- | --------- |
| 발송 소요시간            | 345,288ms  | 340,547ms  | **-1.4%** |
| 발송 처리량              | 28.96건/초 | 29.36건/초 | **+1.4%** |
| 접수 시간(`queueMillis`) | 25,457ms   | 9,895ms    | **-61%**  |

**발송 처리량은 1.4% 차이로 사실상 같습니다.** worker의 병목이 발송사 지연 200ms이므로
로그 출력 비용이 그 안에 묻힙니다. 따라서 **A·B·E·F의 발송 관련 수치는 유효합니다.**

반면 **접수·`outbox_event` INSERT 경로는 61% 차이**가 났습니다. DB 쓰기가 빠르기 때문에
로그 비용이 그대로 드러납니다. 접수 관련 수치에는 이 비용이 포함돼 있습니다.

측정 D는 프로파일을 적용해 재측정한 값을 실었습니다.

## 측정 정의가 v1과 달라진 점

**v1에서는 발송 API의 응답시간이 곧 발송 소요시간이었습니다.** 발송이 다 끝나야 응답했으니까요.
v2는 즉시 응답하므로 둘이 분리됩니다.

| 지표             | 무엇을 재나                                                            | v1과 비교                           |
| ---------------- | ---------------------------------------------------------------------- | ----------------------------------- |
| `queueMillis`    | 발송 실행 요청부터 **202 응답까지**. `outbox_event`에 지시를 쌓는 시간 | v1에 없던 개념                      |
| `dispatchMillis` | **발송 시작부터 마지막 발송(`max(sent_at)`)까지**                      | **v1의 소요시간과 정의가 같습니다** |

**v1과 나란히 놓고 비교하는 값은 `dispatchMillis`입니다.**

측정 방법도 바뀌었습니다. v1은 응답이 곧 결과라 요청 한 번이면 됐지만, v2는 응답 이후에도
발송이 계속되므로 **현황 조회 API를 반복 호출해 완료를 확인**합니다. 다만 소요시간은 조회 쪽에서
재지 않고 **서버가 기록한 값을 읽어옵니다.** 그래서 조회 간격(5~10초)이나 완료 판정 주기(2초)가
결과에 섞이지 않습니다.

### 측정 스크립트 세 개

`load-test/scripts/` 아래에 있습니다. 무엇을 재는지가 서로 다릅니다.

| 파일                     | 한 줄 요약                                            | 사용 측정 |
| ------------------------ | ----------------------------------------------------- | --------- |
| `create-api.js`          | **접수만** 잽니다. 발송은 아예 하지 않습니다          | D         |
| `dispatch-duration.js`   | **발송**을 잽니다. 10만 건 다 보내는 데 얼마나 걸리나 | A, B, E   |
| `concurrent-dispatch.js` | **발송을 돌려놓고, 그동안 접수를 잽니다**             | C         |

`concurrent-dispatch.js`만 구조가 다릅니다. 두 가지 일을 동시에 합니다.

- **dispatch 시나리오** — 발송을 실행하고 완료될 때까지 붙잡고 있습니다
- **probe 시나리오** — 그동안 접수 API를 **초당 1회** 호출해 응답시간을 기록합니다

"발송이 도는 동안 다른 요청이 살아 있는가"를 재는 것이 목적이므로, **probe가 도는 내내
발송이 진행 중이었어야 측정이 유효**합니다. 이를 확인하려고 발송 실제 소요시간을
`dispatch_wall_duration`으로 함께 기록합니다.

## A. 수신자 규모별 발송 소요시간

발송사 지연 200ms, 파티션 10, 동시성 10 고정입니다.

| 수신자 수 | 접수(`queueMillis`) | 발송(`dispatchMillis`) | 건당    | 처리량         | 성공   | 실패 |
| --------- | ------------------- | ---------------------- | ------- | -------------- | ------ | ---- |
| 100       | 1.6초               | 8.5초                  | 85.14ms | 11.75건/초     | 100    | 0    |
| 10,000    | 9.9초               | 5분 41초               | 34.05ms | 29.36건/초     | 9,999  | 1    |
| 100,000   | 3분 16초 ※          | **55분 29초**          | 33.29ms | **30.03건/초** | 99,997 | 3    |

※ 로그를 켠 상태에서 측정한 값입니다. 10,000건 회차에서 로그를 끄면 접수 시간이 61% 줄었으므로,
실제로는 이보다 상당히 짧습니다.

### 관찰

**10,000건과 100,000건의 처리량이 29.36 → 30.03으로 유지됩니다.**
규모를 10배 늘려도 초당 처리량이 그대로입니다. v1이 "느리지만 일정"했다면 v2는 "빠르면서 일정"합니다.
특정 규모에서 무너지는 지점이 없다는 점은 v1과 같고, 그 수준이 6.8배 높아진 것입니다.

**100건 회차만 11.75건/초로 낮습니다.** 규모가 작아 파티션 10개를 다 채우지 못하고,
poller의 1초 주기가 전체 8.5초 중 큰 비중을 차지하기 때문입니다.
**최소 규모에서는 고정 오버헤드가 지배합니다.**

### 이론값과의 차이

동시에 10건을 처리하고 한 건에 200ms가 걸리므로 이론상 **초당 50건**이 나와야 합니다.
실측은 30.03건/초로 **달성률 60%**입니다.

부족분은 worker가 발송 한 건마다 추가로 하는 DB 작업으로 보입니다.

- `processed_event`에 INSERT (중복 확인)
- `notification_message` 조회
- 발송 결과 UPDATE

발송사 호출 200ms 외에 건당 약 133ms가 더 쓰인 셈입니다.
**이 값을 줄이는 것이 다음 개선 지점입니다.**

### 환산

| 수신자 수 | v1                | v2                |
| --------- | ----------------- | ----------------- |
| 100,000   | 6시간 19분        | 55분 29초         |
| 1,000,000 | 약 63시간 (2.6일) | **약 9시간 15분** |

v1 문서에서 지적한 예약 발송 문제를 다시 보면, 02시에 10만 명 예약 발송 시
**마지막 수신자가 받는 시각이 08시 19분에서 02시 55분**이 됩니다.

### 접수가 즉시 응답하지는 않습니다

10만 건에서 202 응답까지 **3분 16초**가 걸립니다. `outbox_event`에 10만 행을 INSERT하는 시간입니다.
"발송 요청 후 즉시 응답"이라고 표현하기는 어렵습니다.

다만 v1은 이 시점부터 **6시간 19분**을 기다려야 했으므로, 사용자가 붙잡히는 시간은
크게 줄었습니다. 이 3분도 배치 INSERT로 단축할 여지가 있습니다.

## B. 발송사 지연 증가의 영향

수신자 300명 고정, `latencyMs`만 변경했습니다.

| 발송사 지연 | v1        | v2           | 배수      | v2 처리량  |
| ----------- | --------- | ------------ | --------- | ---------- |
| 200ms       | 1분 17초  | **15.1초**   | 5.1배     | 19.87건/초 |
| 1,000ms     | 5분 09초  | **45.0초**   | 6.9배     | 6.67건/초  |
| 3,000ms     | 15분 20초 | **1분 52초** | **8.2배** | 2.67건/초  |

### 관찰

**발송사가 느려질수록 v2의 우위가 커집니다.**

v1은 계수 1.00으로 지연을 그대로 전파했습니다. 발송사가 3초가 되면 소요시간도 정확히 15배가 됐습니다.
v2는 동시에 여러 건을 처리하므로 지연의 일부를 흡수합니다. 그래서 지연이 클수록 격차가 벌어집니다.

발송사가 3초로 느려졌을 때 10만 건 환산치는 **v1 약 85시간(3.5일) → v2 약 10시간 24분**입니다.
v1에서는 발송사의 일시적 성능 저하가 며칠짜리 장애가 됐지만, v2에서는 하루 안에 끝납니다.

> 300건은 표본이 작아 처리량 절대값의 신뢰도가 낮습니다.  
> 파티션 10개에 300건을 나누면 파티션당 30건이라 병렬 슬롯을 충분히 채우지 못하고, poller 주기와 리밸런싱 시간이 상대적으로 크게 잡힙니다.  
> **B는 지연에 따른 기울기를, A는 처리량의 절대값을 측정한 것**으로 해석하는 편이 정확합니다.  
> v1 문서도 같은 이유로 B의 고정비를 신뢰하지 않았습니다.

## C. 동시 발송 시 접수 API 응답

발송을 동시에 실행해두고, 그동안 접수 API를 초당 1회 호출해 응답시간을 측정했습니다.

|               | v1 (동시 발송 200건) | v2                   |
| ------------- | -------------------- | -------------------- |
| p(50)         | 87.32ms              | **29.05ms**          |
| p(95)         | **56.99초**          | **644.5ms**          |
| p(99)         | 1분 01초             | 4.92초               |
| max           | —                    | 6.19초               |
| 1초 이내 응답 | 50.87%               | **95.00%** (114/120) |
| 요청 실패     | —                    | 0% (0/715)           |

`dispatch_wall_duration` 평균 **9분 36초** — probe가 도는 내내 발송이 진행 중이었으므로
측정이 유효합니다.

### 관찰

**v1의 병목이었던 Tomcat 스레드 고갈이 사라졌습니다.**

v1은 발송 하나가 스레드 하나를 `수신자 수 × 발송사 지연`만큼 붙잡았습니다.  
동시 발송 200건이면 기본 스레드 200개가 전부 묶여서, 접수 요청은 스레드를 받지 못하고 **발송이 끝날 때까지 그대로 멈춰 있었습니다.**

v2는 발송 실행 API가 지시만 적고 즉시 반환하므로 스레드를 오래 붙잡지 않습니다.  
실제 발송은 별도 프로세스인 worker에서 일어나므로 API 스레드와 무관합니다.  
**구조적으로 이 병목이 발생할 수 없게 됐습니다.**

### 완전한 격리는 아닙니다

p(99)가 4.92초, 최대 6.19초입니다. 1초를 넘긴 요청이 120번 중 6번 있었습니다.

원인은 **DB를 공유하기 때문**입니다.
발송 실행이 `outbox_event`에 대량 INSERT를 하는 동안 접수 API도 같은 DB에 INSERT를 합니다.
커넥션 풀과 디스크를 놓고 경합합니다.

**"발송이 접수를 막는다"에서 "발송이 접수를 느리게 한다"로 바뀐 것**이지 완전히 분리된 것은 아닙니다.
정확히는 초 단위 대기가 밀리초 단위 지연이 됐습니다.

### 측정상 유의사항

- **v1은 동시 발송 200건에서 측정했습니다.** v2가 다른 조건이라면 직접 비교가 아닙니다. 본 회차의 동시 발송 수를 확인해 명시해야 합니다.
- `dropped_iterations`는 발생하지 않았습니다. 느린 샘플이 통계에서 빠지지 않았습니다.
- k6 요약의 `http_req_duration`(p95 81.24ms)은 접수·발송실행·현황조회가 모두 섞인 값이므로 이 절의 결론에 사용하지 않았습니다. 접수만 따로 기록한 `probe_create_duration`을 썼습니다.

## D. 접수 API 응답시간

발송을 실행하지 않은 상태에서 접수 API만 측정했습니다. 수신자 1,000명 / VU 20 / 1분.

|        | v1         | v2             |
| ------ | ---------- | -------------- |
| p(50)  | 2.09초     | **5.23초**     |
| p(95)  | 3.68초     | **7.91초**     |
| p(99)  | 5.04초     | 9.24초         |
| 처리량 | 9.18 req/s | **3.70 req/s** |
| 행/초  | **9,177**  | **3,699**      |
| 실패   | 0%         | 0%             |

**이 항목만 v1보다 나빠졌습니다. 2.5배 느립니다.**

### 확인한 것

접수 API의 코드는 v1과 v2가 동일합니다. 구조 변경은 발송 경로에만 일어났습니다.
따라서 코드 문제는 아니며, 환경 차이로 보입니다. 측정 과정에서 두 가지를 배제했습니다.

- **로그 설정** — `loadtest` 프로파일을 적용해 2.07 → 3.70 req/s로 개선됐습니다. 원인의 일부였지만 전부는 아닙니다.
- **테이블 파편화** — `TRUNCATE`로 완전히 비우고 재측정했으나 변화가 없었습니다.
- **백그라운드 스케줄러** — outbox poller와 완료 판정을 모두 끄고 측정했으나 변화가 없었습니다.

### 남은 후보

- **Kafka 브로커(Docker)의 자원 경합**
  - v1 측정 환경에는 없던 프로세스입니다.
  - Docker Desktop의 WSL2 VM이 호스트 메모리를 점유하면 MySQL 버퍼 풀과 OS 페이지 캐시에 쓸 수 있는 양이 줄어듭니다.
  - 접수 API는 INSERT 집약적이라 영향을 받을 수 있습니다.
- **worker JVM이 추가로 상주**하면서 CPU와 메모리를 나눠 씁니다.

**원인을 확정하지 못했습니다.**

v1 문서는 HikariCP 메트릭(`active`가 10에 고정, `pending`이 9~10)을 관찰해 병목이 커넥션 풀임을 확정했습니다.
**v2에서는 같은 수준의 확인을 하지 못했으므로 위 후보는 가설로만 남깁니다.**

### v1이 남긴 예고

v1 문서는 이렇게 적었습니다.

> **DB 커넥션 풀을 파티션 수와 함께 설계해야 합니다.** 컨슈머를 늘려 병렬로 처리하더라도 DB 커넥션을 확보하지 못하면 처리량이 따라오지 않습니다.

측정 A와 E에서 나온 **이론값 대비 달성률 54~67%**가 이 예고와 관련 있을 가능성이 있습니다.  
worker도 커넥션 풀 기본값 10을 쓰고 있으며, 동시성을 20으로 올렸을 때 달성률이 가장 낮았습니다.  
**이 역시 확인이 필요한 가설입니다.**

## E. 파티션 수와 처리량

**v2에서 새로 생긴 측정이며, 이 문서의 핵심입니다.**

수신자 10,000명 고정. 토픽 파티션 수와 worker 동시성을 같은 값으로 맞춰가며 측정했습니다.

| 파티션 / 동시성 | 소요시간     | 처리량         | 이론값   | 달성률 |
| --------------- | ------------ | -------------- | -------- | ------ |
| 5               | 10분 01초    | 16.64건/초     | 25건/초  | 67%    |
| 10              | 5분 21초     | 31.12건/초     | 50건/초  | 62%    |
| 20              | **3분 05초** | **54.02건/초** | 100건/초 | 54%    |

이론값은 `동시 처리 개수 ÷ 발송사 지연(0.2초)`입니다.

### 관찰

**파티션을 2배로 늘리면 처리량이 약 1.8배가 됩니다.**

- 5 → 10: **1.87배**
- 10 → 20: **1.74배**

v1에서는 무엇을 바꿔도 4.4건/초로 고정이었습니다.  
**처리량이 구조에 묶인 값에서 설정으로 조절하는 값이 됐다는 것**이 v1 대비 가장 큰 변화입니다.

### 교차 검증

측정 A와 E는 규모가 10배 다른 독립적인 측정인데 결과가 일치합니다.

|        | 규모      | 파티션 | 처리량     |
| ------ | --------- | ------ | ---------- |
| 측정 A | 100,000건 | 10     | 30.03건/초 |
| 측정 E | 10,000건  | 10     | 31.12건/초 |

**규모가 10배 달라도 처리량이 같습니다.** 선형 확장이 두 측정에서 독립적으로 확인됐습니다.

### 비례가 완전하지 않습니다

달성률이 **67% → 62% → 54%**로 떨어집니다. 파티션을 늘릴수록 이론값에서 멀어집니다.

파티션만 늘려서는 이론 처리량에 도달할 수 없으며, **동시 처리 개수가 늘어날수록 다른 자원이 병목으로 드러난다**는 뜻입니다.  
후보는 worker의 DB 커넥션 풀(10), MySQL 쓰기 성능, mock-provider의 처리 한계입니다.

### 목표와의 관계

v1 문서가 세운 목표는 **44건/초**였습니다. 파티션 10으로는 31.12건/초로 미달했지만, **파티션 20에서 54.02건/초로 목표를 넘습니다.**

목표 미달은 구조의 한계가 아니라 파라미터 선택의 문제이며, **목표 달성에 필요한 파티션 수를 측정으로 특정했습니다.**

## F. 밀린 메시지 회복 시간

v1에서는 6시간짜리 발송이 중간에 실패하면 상태가 `DISPATCHING`으로 남아 재실행이 차단됐고(409) 이어서 발송할 수단이 없었습니다.
v2가 이 상황을 어떻게 처리하는지 측정했습니다.

**방법:** worker를 끈 상태로 10만 건을 발송 실행해 Kafka에 쌓아두고, worker를 켠 시점부터 lag이 0이 될 때까지의 시간을 5초 간격으로 관측했습니다.

| 항목        | 값                      |
| ----------- | ----------------------- |
| 시작 lag    | 130,384건               |
| 회복 시간   | **4,073초 (67분 53초)** |
| 회복 처리량 | **31.43건/초**          |

### 관찰

**회복 처리량이 평상시와 같습니다.**

|                            | 처리량         |
| -------------------------- | -------------- |
| 평상시 (측정 E, 파티션 10) | 31.12건/초     |
| 밀린 것 회복 (측정 F)      | **31.43건/초** |

차이가 1%입니다. 여기서 알 수 있는 것은 **outbox poller가 병목이 아니라는 점**입니다.

평상시에는 poller가 1초마다 500건씩 공급하므로 이론상 초당 500건이 상한입니다.
회복 시에는 이미 Kafka에 다 쌓여 있어 poller가 관여하지 않습니다.
**두 경우의 처리량이 같다는 것은 poller 상한(500건/초)이 worker 능력(31건/초)보다 16배 여유가 있어 애초에 걸리지 않았다**는 뜻입니다.

**병목은 worker의 발송 처리입니다.**
발송사 지연을 동시성으로 나눈 값이 처리량을 결정하며, 측정 E가 이를 파티션 수로 조절할 수 있음을 보였습니다.

### 중단 내성

worker를 껐다 켜는 동안 **지시가 하나도 유실되지 않았습니다.**
Kafka가 오프셋으로 "어디까지 읽었는지"를 기억하므로 worker는 그 지점부터 이어서 처리합니다.
v1에서 불가능했던 **중단 후 재개**가 별도 구현 없이 동작합니다.

### 측정상 유의사항

- 시작 lag 130,384건에는 **이전 회차의 잔여 메시지 약 2,400건이 포함**돼 있습니다.
  이들은 DB에 대응 행이 없어 발송사를 호출하지 않고 건너뛰므로 실제 발송보다 빠릅니다.
  전체의 2% 미만이라 처리량에 미치는 영향은 작습니다.
- 5초 간격 폴링이므로 회복 시간에 최대 5초의 오차가 있습니다.

| ------------ | --------------- | ----------------- |
| 처리 건수    | 100,000         | 128,123           |
| 최종 실패    | 2,974건 (2.97%) | **2건 (0.0016%)** |
| 실패 후 처리 | **영구 유실**   | **DLQ에 보존**    |

발송사에 설정한 실패율은 3%입니다. v1은 재시도가 없어 3%가 그대로 최종 실패가 됐습니다.

v2는 **1초 간격으로 2회 재시도**합니다. 3번 모두 실패할 확률은 이론상 `0.03³ = 0.0027%`이고, 실측 0.0016%로 같은 자릿수입니다. **재시도가 설계대로 동작했습니다.**

그리고 실패한 건은 사라지지 않고 `notification.send.dlq` 토픽에 남습니다.
원인을 확인하고 재처리할 수 있습니다.

**3% 실패하는 발송사를 상대로 최종 실패율 0.0016%를 만들었습니다.**

### DLQ 확인

측정 종료 후 DLQ 토픽에 쌓인 메시지는 **총 121건**입니다. (파티션 10개의 오프셋 합)

```
notification.send.dlq:0:11   notification.send.dlq:5:13
notification.send.dlq:1:11   notification.send.dlq:6:13
notification.send.dlq:2:12   notification.send.dlq:7:12
notification.send.dlq:3:12   notification.send.dlq:8:12
notification.send.dlq:4:13   notification.send.dlq:9:12
```

**이 121건은 특정 회차의 실패 수가 아니라 전체 측정 회차의 누적입니다.**
DB는 회차마다 `TRUNCATE`로 비웠지만 DLQ 토픽은 비우지 않았기 때문입니다.
표의 "2건"은 마지막 DB 상태 기준이며, 두 숫자를 직접 비교할 수 없습니다.

**재시도를 소진한 건이 유실되지 않고 DLQ에 보존된다는 사실은 확인됐습니다.**
다만 회차별 실패 수를 분리해 보려면 측정 전에 DLQ 토픽도 함께 비워야 합니다.
이번 측정에서는 그렇게 하지 않았습니다.

## outbox 정합성 검증

발송 지시가 유실되거나 중복되지 않았는지 확인했습니다.

| 확인 항목                                    | 값          |
| -------------------------------------------- | ----------- |
| Kafka 토픽에 발행된 메시지 수 (전 파티션 합) | **200,100** |
| `notification_message` 행 수                 | **200,100** |

**정확히 일치합니다.** 발송 대상 한 건마다 정확히 한 개의 지시가 발행됐습니다.
Transactional Outbox 패턴이 유실도 중복도 없이 동작했습니다.

처리 내역도 맞아떨어집니다.

```
SUCCESS 128,121 + FAIL 2 = 128,123   worker가 실제로 처리
PENDING 71,977                        측정 준비 중 오프셋 리셋으로 건너뛴 분
합계    200,100                       ✓
```

`PENDING` 71,977건은 측정 F를 준비하면서 컨슈머 오프셋을 최신으로 이동시켜 의도적으로 건너뛴 메시지입니다. 장애로 인한 유실이 아닙니다.

## 결론

v1의 한계는 **"구조적으로 일정 속도 이상 낼 수 없다"**였습니다.
v2의 성과는 **"처리량을 설정으로 조절할 수 있게 됐다"**입니다.

1. **처리량이 고정값에서 조절 가능한 값이 됐습니다.**

- v1은 무엇을 해도 4.4건/초였습니다.
- v2는 파티션 수를 5·10·20으로 바꾸면 16.6·31.1·54.0건/초가 됩니다.
- 요구 시간에 맞춰 파티션을 정하면 됩니다.

2. **발송사 지연을 흡수합니다.**

- v1은 계수 1.00으로 그대로 전파했지만,
- v2는 지연이 클수록 우위가 커집니다(3초 지연에서 8.2배).

3. **발송이 다른 요청을 막지 않습니다.**

- 발송이 API 스레드를 점유하지 않으므로 v1에서 발생한 Tomcat 스레드 고갈이 구조적으로 일어나지 않습니다.

4. **중단을 견딥니다.**

- worker가 죽어도 지시는 Kafka에 남아 있고, 다시 켜면 오프셋 위치부터 이어서 처리합니다.
- 밀린 13만 건을 68분에 소진했습니다.

5. **실패가 유실되지 않습니다.**

- 재시도 2회로 최종 실패율이 2.97%에서 0.0016%가 됐고, 그마저도 DLQ에 보존됩니다.

성능 향상만큼 중요한 것은 **한계가 어디인지 알게 됐다는 점**입니다.
v1에서는 "왜 느린가"의 답이 구조 자체였으므로 손댈 곳이 없었습니다.
v2에서는 병목이 worker의 발송 처리이며, 파티션 수로 조절 가능하고, 이론값 대비 54~67%라는 개선 여지가 남아 있다는 것까지 특정됐습니다.

## 남은 병목과 다음 과제

### 1. 이론값 대비 54~67%에 머문다

동시성 10이면 초당 50건이어야 하는데 30건입니다.
부족분은 worker가 발송 한 건마다 수행하는 DB 작업(`processed_event` INSERT, `notification_message` 조회·갱신)으로 추정됩니다.

동시성을 20으로 올렸을 때 달성률이 가장 낮았다는 점(54%)에서 **worker의 DB 커넥션 풀(기본값 10)이 동시성 20을 감당하지 못했을 가능성**이 있습니다.
v1 문서가 예고한 "커넥션 풀을 파티션 수와 함께 설계해야 한다"에 해당합니다.

**확인 방법** — 부하 중 worker의 HikariCP `active`·`pending` 관찰, 커넥션 풀을 20으로 올려 재측정.

### 2. 접수 API가 v1보다 2.5배 느려졌다

9,177행/초 → 3,699행/초. 로그 설정, 테이블 파편화, 백그라운드 스케줄러는 배제했습니다.
Kafka 브로커의 자원 경합이 남은 후보이나 **확정하지 못했습니다.**

**확인 방법** — 부하 중 HikariCP 메트릭 관찰, Kafka를 정지한 상태와 비교.

### 3. 발송 실행이 즉시 응답하지 않는다

10만 건에서 202까지 3분 16초가 걸립니다.
`outbox_event`에 10만 행을 한 건씩 INSERT하기 때문입니다.
JDBC 배치 INSERT로 단축할 여지가 있습니다.

### 4. 발송과 접수가 완전히 분리되지 않았다

접수 API p(99)가 4.92초입니다. 두 경로가 같은 DB와 커넥션 풀을 공유하기 때문입니다.

### 5. 미구현 기능

- **컨슈머 lag 모니터링**
  - 현재는 CLI로 수동 확인합니다. 밀림이 임계치를 넘으면 알림이 가야 운영이 가능합니다.
- **구간 재처리(replay) 어드민 API**
  - DLQ에 쌓인 메시지나 특정 구간을 다시 발송하는 수단이 없습니다.
  - `eventId`를 새로 발급하면 중복 방지에 걸리지 않고 재처리할 수 있도록 설계는 돼 있습니다.

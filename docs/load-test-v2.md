# v2 부하 테스트 결과

## 1. v1에서 발견한 문제

v1 부하 테스트를 통해 다음 문제를 확인했습니다.

1. 순차 처리로 인해 처리량을 늘리기 어렵다.
2. 외부 발송사의 지연을 그대로 받는다.
3. 대량 발송이 다른 API까지 막을 수 있다.
4. 실패한 발송을 다시 처리할 방법이 없다.

v2에서는 실제 발송을 API 요청 처리에서 분리하고, 여러 발송을 병렬로 처리하면서 실패하거나 Worker가 중단된 상황에서도 다시 처리할 수 있도록 구조를 변경했습니다.

## 2. 변경한 구조

### 1) Kafka 비동기 처리

v1에서는 발송 API를 호출하면 해당 요청을 처리하는 Tomcat Thread가 모든 수신자를 한 명씩 순차적으로 발송했습니다.

```text
발송 API
   ↓
수신자 1 발송
   ↓
수신자 2 발송
   ↓
...
   ↓
모든 발송 완료
   ↓
API 응답
```

수신자가 많아질수록 하나의 요청이 Thread를 오래 점유하고, 이런 발송 요청이 동시에 많아지면 다른 API까지 처리하지 못하는 문제가 있었습니다.

v2에서는 API가 직접 발송하지 않고 발송해야 할 작업만 등록하고, 실제 발송은 별도의 Worker가 Kafka 메시지를 받아 처리하도록 변경했습니다.

```text
발송 API
   ↓
발송 지시 저장
   ↓
API 응답

outbox_event
   ↓
Kafka
   ↓
Worker
   ↓
실제 발송
```

Worker에서는 Kafka Consumer가 메시지를 처리하며, 파티션 수와 Consumer 동시성을 이용해 여러 발송을 동시에 처리할 수 있도록 했습니다.

기본 부하 테스트에서는 Kafka 파티션과 Consumer 동시성을 각각 10으로 설정했습니다.

### 2) Transactional Outbox

DB 상태 변경과 Kafka 메시지 발행은 하나의 트랜잭션으로 처리할 수 없습니다.

예를 들어 DB에는 발송을 시작했다고 저장했는데 Kafka에 메시지를 보내기 전에 서버가 종료되면, DB에는 발송 중으로 남아 있지만 실제 발송 지시는 Kafka에 전달되지 않을 수 있습니다.

이를 방지하기 위해 발송 API에서 Kafka에 바로 메시지를 보내지 않고, DB 트랜잭션 안에서 발송 상태 변경과 함께 `outbox_event`를 저장하도록 했습니다.

```text
발송 API
   ↓
notification 상태 변경
+
outbox_event 저장
   ↓
DB Transaction Commit
```

이후 별도의 Poller가 `PENDING` 상태의 Outbox 데이터를 읽어 Kafka로 발행합니다.

Kafka 발행에 실패하면 Outbox 데이터가 남아 있기 때문에 다음 Polling에서 다시 시도할 수 있습니다.

### 3) processed_event를 이용한 중복 처리 방지

Kafka는 상황에 따라 같은 메시지를 다시 전달할 수 있습니다.

같은 발송 지시를 Worker가 다시 처리하면 사용자에게 동일한 알림이 중복 발송될 수 있습니다.

이를 방지하기 위해 Worker에서 처리한 `eventId`를 `processed_event`에 기록하고, 이미 처리한 이벤트가 다시 들어오면 실제 발송을 다시 실행하지 않도록 했습니다.

### 4) Retry / DLQ

v1에서는 외부 발송사가 실패를 반환하면 해당 발송을 바로 실패 처리했습니다.

v2에서는 발송에 실패하면 같은 메시지를 다시 처리하도록 재시도를 추가했습니다.

```text
최초 발송
   ↓ 실패
1차 재시도
   ↓ 실패
2차 재시도
   ↓ 실패
DLQ
```

## 3. 동일 조건에서 다시 측정

## A. 수신자 규모별 발송 소요시간

**조건:** `mock-provider`의 지연시간(`latencyMs`) 200ms, Kafka 파티션 10, Consumer 동시성 10 고정

v1과 동일하게 실제 발송이 시작된 시점부터 마지막 수신자의 발송이 끝날 때까지 걸린 시간(`dispatchMillis`)을 측정했습니다.

| 수신자 수 | 발송 소요시간 |    건당 |   성공 | 실패 |     실패율 |
| --------- | ------------: | ------: | -----: | ---: | ---------: |
| 100       |        6.11초 | 61.10ms |    100 |    0 |         0% |
| 1,000     |       31.98초 | 31.98ms |  1,000 |    0 |         0% |
| 10,000    |      5분 05초 | 30.52ms | 10,000 |    0 |         0% |
| 100,000   | **48분 56초** | 29.36ms | 99,999 |    1 | **0.001%** |

1,000건 이상에서는 수신자 수가 증가해도 약 31~34건/초의 처리량을 유지했습니다.

```text
1,000명   → 31.27건/초
10,000명  → 32.77건/초
100,000명 → 34.06건/초
```

특정 수신자 수를 넘어가면서 처리량이 급격하게 떨어지는 현상은 확인되지 않았습니다.

100건에서는 Kafka 발행과 Polling 등 고정적으로 발생하는 작업의 비중이 상대적으로 커 처리량이 낮게 측정된 것으로 보입니다.

> 표의 `건당`은 `dispatchMillis ÷ 전체 수신자 수`로 계산한 값입니다.  
> 실제 알림 하나가 29ms 만에 발송된다는 의미가 아니라 병렬 처리된 전체 발송시간을 수신자 수로 나눈 값입니다.

#### 발송 지시 적재 시간

v2에서는 실제 발송시간과 별개로 발송 지시를 Outbox에 저장하고 API가 `202 Accepted`를 반환할 때까지 걸린 시간인 `queueMillis`도 측정했습니다.

| 수신자 수 |  queueMillis |
| --------- | -----------: |
| 100       |        165ms |
| 1,000     |        630ms |
| 10,000    |      12.30초 |
| 100,000   | **1분 15초** |

실제 발송은 Worker로 분리됐지만, 발송 지시를 Outbox에 저장하는 작업은 아직 발송 실행 API 안에서 처리됩니다.

따라서 수신자 수가 많아질수록 API 응답까지 걸리는 시간도 증가했습니다.

## B. 발송사 지연 증가의 영향

**조건:** 수신자 300명 고정, `mock-provider`의 지연시간(`latencyMs`)만 변경

| 발송사 지연 | 발송 소요시간 |     건당 | 성공 | 실패 |
| ----------- | ------------: | -------: | ---: | ---: |
| 200ms       |        15.1초 |  50.32ms |  300 |    0 |
| 1,000ms     |        45.0초 | 149.92ms |  299 |    1 |
| 3,000ms     |      1분 52초 | 374.24ms |  300 |    0 |

발송사의 응답이 느려지면서 전체 발송시간도 증가했습니다.

다만 여러 Consumer가 동시에 메시지를 처리하기 때문에 하나의 발송이 끝날 때까지 기다린 뒤 다음 수신자를 처리하던 v1과는 다르게, 여러 발송의 외부 API 대기시간을 동시에 처리할 수 있습니다.

발송사 지연시간은 200ms에서 3,000ms로 15배 증가했지만 전체 발송시간은 15.1초에서 약 1분 52초로 약 7.4배 증가했습니다.

중간에 발송 실패가 발생하더라도 재시도가 성공하면 최종 결과는 `SUCCESS`로 변경됩니다.

## C. 동시 발송 시 접수 API 응답

**조건:** 하나의 발송 요청당 수신자 200명으로 고정, 동시에 실행하는 발송 요청 수를 변경
발송이 진행되는 동안 접수 API(`/api/test/notifications`)를 초당 1회 호출하여 응답시간(`probe_create_duration`)을 측정했습니다.

| 동시 발송 수 |   p(50) |      p(95) |    p(99) | 1초 이내 응답 |
| ------------ | ------: | ---------: | -------: | ------------: |
| 50           | 13.12ms |    20.59ms | 279.33ms |          100% |
| 100          | 13.60ms |    31.48ms |   1.28초 |        97.50% |
| 200          | 14.02ms | **7.66초** |  12.18초 |        90.08% |
| 250          | 14.16ms | **8.41초** |  11.99초 |        85.12% |

동시 발송 50~100건까지는 접수 API의 p(95)가 20~31ms 수준으로 큰 영향을 받지 않았습니다.

동시 발송이 200건 이상이 되면서 일부 접수 요청의 응답시간이 크게 증가했습니다.

다만 v1에서 동시 발송 200건을 처리할 때처럼 발송 작업이 Tomcat Thread를 장시간 모두 점유해 접수 API가 거의 멈추는 현상과는 다른 결과가 나타났습니다.

v2에서는 동시 발송 200건에서도 p(50)이 약 14ms로 유지됐고, 250건에서도 전체 요청의 약 85%가 1초 안에 응답했습니다.

실제 발송은 Worker로 분리했지만 `notification-api`의 Outbox 저장과 Worker의 발송 결과 저장이 같은 MySQL을 사용하고 있습니다.

따라서 대량의 DB 작업이 동시에 발생하면서 일부 요청이 느려졌을 가능성이 있지만, 이번 테스트만으로 정확한 병목 자원을 특정하지는 못했습니다.

## D. 접수 API 응답시간

발송을 실행하지 않고 접수 API(`/api/test/notifications`) 자체의 성능만 측정했습니다.

VU(Virtual User)는 동시에 요청을 반복해서 보내는 가상 사용자 수입니다.

예를 들어 VU가 10이면 10개의 가상 사용자가 각각 요청을 보내고, 응답을 받은 뒤 다시 다음 요청을 보내는 작업을 반복합니다.

| 수신자 수 |  VU |      p(50) |      p(95) |       p(99) |      처리량 |     행/초 |
| --------- | --: | ---------: | ---------: | ----------: | ----------: | --------: |
| 100       |  10 |   338.08ms |   661.35ms |    841.01ms | 27.16 req/s |     2,716 |
| 1,000     |  10 |     1.39초 |     1.91초 |      2.42초 |  6.83 req/s | **6,831** |
| 1,000     |  20 | **5.03초** | **8.24초** | **10.09초** |  4.07 req/s | **4,069** |

실패율은 모든 구간에서 0%였습니다.

수신자 수를 100명에서 1,000명으로 늘리면 하나의 요청에서 저장해야 하는 `notification_message`의 수가 증가하기 때문에 응답시간도 길어졌습니다.

반면 행 처리량은 2,716행/초에서 6,831행/초로 증가했습니다.

요청마다 발생하는 HTTP 처리, 트랜잭션 시작 및 Commit 등의 고정 비용이 있기 때문에 한 번에 더 많은 데이터를 저장했을 때 행 기준 처리량이 높아진 것으로 볼 수 있습니다.

수신자 1,000명 조건에서 VU를 10에서 20으로 늘렸을 때는 처리량이 증가하지 않고 오히려 감소했습니다.

```text
VU 10
6.83 req/s
6,831행/초

↓

VU 20
4.07 req/s
4,069행/초
```

## 4. v1 ↔ v2 비교

### 1. 대량 발송

| 항목                    |          v1 |             v2 |
| ----------------------- | ----------: | -------------: |
| 100,000건 발송 소요시간 |  6시간 19분 |  **48분 56초** |
| 발송 처리량             | 약 4.4건/초 | **34.06건/초** |
| 최종 실패               |     2,974건 |        **1건** |

10만 건 발송시간은 6시간 19분에서 48분 56초로 약 **7.7배 단축**됐습니다.

v1에서는 한 건씩 순차적으로 처리했기 때문에 처리량이 약 4.4건/초로 제한됐지만, v2에서는 Kafka Consumer의 병렬 처리를 통해 약 34건/초까지 증가했습니다.

### 2. 외부 발송사 지연

수신자 300명, 발송사 지연 3초 기준으로 비교하면 다음과 같습니다.

|          |        v1 |           v2 |
| -------- | --------: | -----------: |
| 발송시간 | 15분 20초 | **1분 52초** |

v1은 외부 발송사의 응답을 한 건씩 기다렸기 때문에 지연시간이 그대로 전체 발송시간에 누적됐습니다.

v2에서는 여러 Consumer가 동시에 발송을 진행하기 때문에 외부 API의 대기시간을 병렬로 처리할 수 있었습니다.

### 3. 동시 발송 중 접수 API

| 동시 발송 수 |    v1 p(95) |    v2 p(95) |
| ------------ | ----------: | ----------: |
| 50           |     19.46ms |     20.59ms |
| 100          |     79.92ms | **31.48ms** |
| 200          | **56.99초** |  **7.66초** |
| 250          | **58.60초** |  **8.41초** |

v1에서는 동시 발송 200건에서 발송 요청이 Tomcat Thread를 장시간 점유하면서 다른 API 요청까지 대기하는 문제가 발생했습니다.

v2에서는 실제 발송을 Worker로 분리하면서 v1과 같은 장시간의 Tomcat Thread 고갈 현상은 재현되지 않았습니다.

다만 동시 발송 200건 이상에서는 일부 접수 요청의 응답시간이 다시 증가했기 때문에 다른 자원의 병목은 추가로 확인할 필요가 있습니다.

### 4. 접수 API

| 조건            | v1 행/초 | v2 행/초 |
| --------------- | -------: | -------: |
| 100명 / VU 10   |    4,583 |    2,716 |
| 1,000명 / VU 10 |   10,303 |    6,831 |
| 1,000명 / VU 20 |    9,177 |    4,069 |

접수 API 자체의 처리량은 v1보다 낮아졌습니다.

v2에서 구조적으로 변경한 부분은 주로 발송 경로이기 때문에, 현재 결과만으로 Kafka 적용 자체가 접수 API 성능 저하의 원인이라고 볼 수는 없습니다.

Kafka Broker와 Worker가 같은 장비에서 실행되고 있는 점, DB 자원 경합이나 커넥션 풀 등의 영향을 추가로 확인할 필요가 있습니다.

## 5. Kafka 병렬 처리 확인

**조건:** 수신자 수를 10,000명 고정, Kafka 파티션 수와 Worker Consumer 동시성을 같은 값으로 변경

| 파티션 / 동시성 |     소요시간 |         처리량 |   이론값 | 달성률 |
| --------------- | -----------: | -------------: | -------: | -----: |
| 5               |    10분 01초 |     16.64건/초 |  25건/초 |    67% |
| 10              |     5분 21초 |     31.12건/초 |  50건/초 |    62% |
| 20              | **3분 05초** | **54.02건/초** | 100건/초 |    54% |

파티션 수와 Consumer 동시성을 늘리면서 실제 처리량도 함께 증가했습니다.

v1에서는 하나의 요청 안에서 한 건씩 순차적으로 처리하기 때문에 처리량을 구조적으로 늘리기 어려웠습니다.

v2에서는 파티션과 Consumer 동시성을 조절해 동시에 처리할 수 있는 메시지 수를 늘릴 수 있게 됐습니다.

다만 파티션을 2배로 늘렸을 때 처리량이 정확히 2배 증가하지는 않았습니다.

이론값 대비 달성률도 67% → 62% → 54%로 감소했습니다.

동시성을 높일수록 Worker의 DB 작업이나 커넥션 풀 등 다른 자원이 새로운 병목으로 나타날 가능성이 있습니다.

## 6. 장애 복구 테스트

Worker가 동작하지 않는 동안 Kafka에 메시지를 쌓아둔 뒤, Worker를 다시 실행했을 때 밀려 있는 메시지를 정상적으로 처리할 수 있는지 확인했습니다.

**조건:** worker를 끈 상태로 대량의 발송 메시지를 Kafka에 쌓아두고, worker를 실행한 시점부터 Consumer lag이 0이 될 때까지 측정

| 항목        |                      값 |
| ----------- | ----------------------: |
| 시작 lag    |               130,384건 |
| 회복 시간   | **4,073초 (67분 53초)** |
| 회복 처리량 |          **31.43건/초** |

Worker가 중단되어 있는 동안에도 메시지는 Kafka에 남아 있었습니다.

Worker를 다시 실행하자 쌓여 있던 메시지를 이어서 처리했고, 약 31.43건/초의 처리량으로 lag을 줄였습니다.

파티션 10에서 평상시 측정한 처리량 31.12건/초와 거의 비슷한 값이 나왔습니다.

따라서 메시지가 이미 Kafka에 많이 쌓여 있는 상황에서도 Worker의 처리량 자체가 크게 떨어지지는 않았습니다.

> 시작 lag 130,384건에는 이전 테스트에서 남은 메시지 약 2,400건이 포함되어 있습니다. 전체의 2% 미만이지만 정확한 10만 건 단독 측정값은 아닙니다.

또한 이번 테스트는 **Worker가 이미 메시지를 처리하는 도중 강제로 종료한 장애 상황을 재현한 것은 아닙니다.**

Worker가 꺼진 상태에서 메시지를 쌓고 다시 실행했을 때 정상적으로 처리할 수 있다는 것까지만 확인했습니다.

## 7. 해결된 문제

### 1) 실제 발송을 API 요청에서 분리

v1에서는 실제 발송이 끝날 때까지 Tomcat Thread가 해당 요청을 계속 처리했습니다.

v2에서는 API가 발송 지시를 등록하고 실제 발송은 별도의 Worker가 처리하도록 분리했습니다.

그 결과 대량 발송 작업이 API 요청 Thread를 발송이 끝날 때까지 장시간 점유하지 않게 됐습니다.

### 2) 병렬 처리 가능

Kafka 파티션과 Consumer 동시성을 이용해 여러 메시지를 동시에 처리할 수 있게 됐습니다.

실제 테스트에서도 파티션을 5 → 10 → 20으로 늘리면서 처리량이 16.64 → 31.12 → 54.02건/초로 증가했습니다.

### 3) 외부 발송사의 지연 영향 감소

v1에서는 외부 발송사의 응답을 한 건씩 기다려야 했습니다.

v2에서는 여러 발송을 동시에 처리할 수 있기 때문에 외부 API 응답을 기다리는 동안 다른 메시지도 함께 처리할 수 있습니다.

### 4) 실패 재시도

발송에 실패하면 최대 2회 재시도하여 최초 요청을 포함해 총 3번 발송을 시도합니다.

재시도 이후에도 실패하면 메시지를 DLQ에 보관합니다.

### 5) Worker가 중단된 동안 메시지 보존

Worker가 동작하지 않더라도 Kafka에 발송 메시지가 남아 있으며, Worker를 다시 실행하면 쌓인 메시지를 다시 처리할 수 있음을 확인했습니다.

## 8. 아직 남은 문제

### 1) Outbox 적재 시간이 길다

실제 발송은 비동기로 분리했지만 발송 실행 API에서는 수신자별 `outbox_event`를 생성합니다.

10만 건에서는 이 작업에 약 1분 15초가 걸렸습니다.

따라서 현재 구조를 완전히 즉시 응답하는 비동기 API라고 보기는 어렵습니다.

Batch Insert 등을 적용해 Outbox 생성 시간을 줄일 수 있는지 확인할 필요가 있습니다.

### 2) 실제 처리량이 이론값보다 낮다

발송사 지연 200ms, Consumer 동시성 10이라면 단순 계산으로는 초당 약 50건을 처리할 수 있습니다.

하지만 실제 처리량은 약 31~34건/초였습니다.

Worker에서는 실제 발송 외에도 `processed_event` 저장, `notification_message` 조회 및 상태 변경과 같은 DB 작업이 발생합니다.

파티션과 동시성을 늘릴수록 이론값 대비 달성률이 낮아졌기 때문에 DB 커넥션 풀이나 DB 작업 등이 병목인지 추가 측정할 필요가 있습니다.

### 3) 동시 발송이 많아지면 일부 접수 요청이 느려진다

v1의 Tomcat Thread 고갈 문제는 크게 개선됐지만 동시 발송 200건 이상에서는 접수 API의 p(95)가 7~8초까지 증가했습니다.

실제 발송은 Worker로 분리했더라도 API와 Worker가 같은 DB를 사용하고 있기 때문에 완전히 서로 영향을 받지 않는 구조는 아닙니다.

어떤 자원이 병목인지 확인하기 위해 HikariCP와 DB 관련 메트릭을 함께 측정할 필요가 있습니다.

### 4) 접수 API 자체의 처리량이 감소했다

수신자 1,000명 / VU 20 기준으로 v1은 9,177행/초였지만 v2에서는 4,069행/초가 측정됐습니다.

현재 결과만으로 원인은 확인하지 못했습니다.

Kafka Broker와 Worker가 같은 장비에서 실행되는 환경 차이, DB 커넥션 풀, CPU와 메모리 자원 경합 등을 추가로 확인할 필요가 있습니다.

### 5) 처리 도중 Worker가 종료되는 상황은 추가 검증이 필요하다

현재 장애 관련 테스트는 Worker를 끈 상태에서 메시지를 쌓고 다시 실행하는 방식으로 진행했습니다.

실제로 Consumer가 메시지를 처리하는 도중 Worker 프로세스가 종료됐을 때 중복 발송이나 누락 없이 정상적으로 이어서 처리되는지는 별도의 테스트가 필요합니다.

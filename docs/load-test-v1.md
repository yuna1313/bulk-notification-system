# v1 부하 테스트 결과

## 1. v1을 만든 이유

Kafka를 공부하면서 처음부터 Kafka를 적용한 프로젝트를 만들면, 왜 Kafka가 필요한지 제대로 이해하기 어려울 것 같았습니다.

그래서 먼저 수신자를 한 명씩 동기 방식으로 처리하는 가장 단순한 v1을 만들었습니다.
v1에서 직접 부하 테스트를 진행해 어떤 문제가 발생하는지 확인하고, 이후 v2에서 Kafka를 적용해 이 문제들을 개선하는 방식으로 진행하고자 했습니다.

## 2. v1 구조

v1에서는 발송 요청이 들어오면 API 서버가 **직접** 모든 수신자에게 발송합니다.

```
발송 요청
    ↓
notification-api
    ↓
수신자 목록 조회
    ↓
수신자 1명씩 순차 처리
    ↓
mock-provider 호출
    ↓
발송 결과 DB 저장
    ↓
다음 수신자 처리
    ↓
모든 수신자 발송 완료 후 API 응답
```

발송 과정에서는 수신자 목록을 조회한 뒤 for문으로 한 명씩 처리합니다.  
각 수신자마다 mock-provider를 호출하고 응답을 받은 후 결과를 DB에 저장한 후에 다음 수신자를 처리합니다.  
비동기 처리, 별도의 발송 Worker, 재시도, 배치 처리는 적용하지 않았습니다.

## 3. 측정 내용

### A. 수신자 규모별 발송 소요시간

**조건:** `mock-provider`의 지연시간(`latencyMs`) 200ms 고정  
발송 실행 API(`/api/notifications/{id}/dispatch`)에서 발송을 시작한 시점부터 모든 수신자에 대한 발송이 끝날 때까지의 시간(`elapsedMillis`)을 측정했습니다.

| 수신자 수 | 발송 소요시간  | 건당     | 성공   | 실패  | 실패율 |
| --------- | -------------- | -------- | ------ | ----- | ------ |
| 100       | 22.5초         | 224.78ms | 95     | 5     | 5.00%  |
| 1,000     | 3분 45초       | 224.69ms | 976    | 24    | 2.40%  |
| 10,000    | 37분 47초      | 226.68ms | 9,731  | 269   | 2.69%  |
| 100,000   | **6시간 19분** | 227.41ms | 97,026 | 2,974 | 2.97%  |

수신자 수가 증가해도 건당 소요시간은 약 225~227ms로 거의 변하지 않았습니다.  
즉, 특정 수신자 수를 넘어가면서 갑자기 성능이 떨어지는 것이 아니라 한 건씩 순차적으로 처리하기 때문에 처음부터 처리량에 한계가 있는 구조였습니다.  
건당 약 226ms가 걸리기 때문에 처리량은 약 4.4건/초이고, 수신자가 늘어난 만큼 전체 발송시간도 거의 비례해서 늘어났습니다.  
10만 명에게 발송하면 모든 발송을 완료하는 데 6시간 19분이 걸렸습니다.

### B. 발송사 지연 증가의 영향

**조건:** 수신자 300명 고정, `mock-provider`의 지연시간(`latencyMs`)만 변경

| 발송사 지연 | 발송 소요시간 | 건당       | 성공 | 실패 |
| ----------- | ------------- | ---------- | ---- | ---- |
| 200ms       | 1분 17초      | 257.06ms   | 293  | 7    |
| 1,000ms     | 5분 09초      | 1,031.66ms | 296  | 4    |
| 3,000ms     | 15분 20초     | 3,067.48ms | 290  | 10   |

발송사의 응답이 느려지자 건당 발송시간도 거의 같은 만큼 증가했습니다.  
v1은 한 건을 발송한 뒤 발송사의 응답이 올 때까지 기다려야 다음 수신자를 처리할 수 있기 때문에, 외부 발송사의 지연시간을 그대로 영향을 받는 구조였습니다.  
발송사가 일시적으로 느려지면 전체 발송시간도 그만큼 길어집니다.

### C. 동시 발송 시 다른 API에 미치는 영향

**조건:** 하나의 발송 요청당 수신자 200명으로 고정, 동시에 실행하는 발송 요청 수를 변경
발송이 진행되는 동안 접수 API(`/api/test/notifications`)를 초당 1회 호출하여 응답시간(`probe_create_duration`)을 측정했습니다.

| 동시 발송 수 | p(50)      | p(95)       | p(99)    | 1초 이내 응답 |
| ------------ | ---------- | ----------- | -------- | ------------- |
| 50           | 13.01ms    | 19.46ms     | 24.40ms  | 사실상 100%   |
| 100          | 17.86ms    | 79.92ms     | 129.31ms | 사실상 100%   |
| 200          | 87.32ms    | **56.99초** | 1분 01초 | 50.87%        |
| 250          | **2.40초** | **58.60초** | 1분 03초 | 49.10%        |

동시 발송이 100건일 때까지는 접수 API가 정상적으로 응답했지만, 200건이 되자 p(95)가 79.92ms에서 56.99초로 크게 증가했습니다.  
v1에서는 하나의 발송 요청을 처리하는 동안 Tomcat 스레드 하나가 계속 사용됩니다.  
측정 환경의 Tomcat 최대 스레드 수가 200개였기 때문에 동시 발송 200건이 실행되자 발송 요청이 스레드를 모두 점유했고, 새로운 접수 요청이 처리될 스레드를 바로 할당받지 못했습니다.  
250건에서는 p(50)도 2.4초까지 증가했습니다. 일부 요청만 느려지는 것이 아니라 일반적인 요청에도 영향을 주기 시작한 것을 확인할 수 있었습니다.

### D. 접수 API 응답시간

발송을 실행하지 않은 상태에서 접수 API(`/api/test/notifications`)만 측정했습니다.

| 수신자 수 | VU  | p(50)      | p(95)    | p(99)    | 처리량      | 행/초      |
| --------- | --- | ---------- | -------- | -------- | ----------- | ---------- |
| 100       | 10  | 219.44ms   | 434.03ms | 705.92ms | 45.83 req/s | 4,583      |
| 1,000     | 10  | 922.13ms   | 1.28초   | 1.40초   | 10.30 req/s | **10,303** |
| 1,000     | 20  | **2.09초** | 3.68초   | 5.04초   | 9.18 req/s  | **9,177**  |

수신자 1,000명에서 VU를 10에서 20으로 늘렸지만 처리량은 증가하지 않았고, 오히려 응답시간이 크게 증가했습니다.  
접수 API는 하나의 요청 안에서 수신자 수만큼 notification_message를 저장하며, 이 작업 전체가 하나의 트랜잭션으로 처리됩니다.  
측정 당시 DB 커넥션 풀의 최대 크기는 10이었고, 부하를 주는 동안 10개의 커넥션이 모두 사용되고 나머지 요청이 커넥션을 기다리는 것을 확인했습니다.  
따라서 이 테스트에서는 MySQL 자체의 최대 쓰기 성능보다 DB 커넥션 풀과 긴 트랜잭션 범위가 먼저 병목으로 나타났습니다.  
발송 API에서는 Tomcat 스레드가 병목이었던 것과 달리, 접수 API에서는 DB 커넥션 풀이 병목이 된 것입니다.

## 4. 결과

v1을 테스트하면서 같은 서비스 안에서도 상황에 따라 다른 문제가 발생하는 것을 확인했습니다.

| 테스트           | 확인한 내용                                                                  |
| ---------------- | ---------------------------------------------------------------------------- |
| 수신자 수 증가   | 건당 소요시간은 일정하지만 순차 처리라 전체 시간이 수신자 수에 비례해서 증가 |
| 발송사 지연 증가 | 외부 발송사의 응답 지연이 전체 발송시간에 그대로 반영                        |
| 동시 발송 증가   | 발송 요청이 Tomcat 스레드를 오래 점유해 다른 API까지 영향을 받음             |
| 접수 API 부하    | 긴 트랜잭션으로 DB 커넥션 풀이 먼저 포화됨                                   |

## 5. 확인한 문제

### 1) 순차 처리로 인해 처리량을 늘리기 어렵다.

수신자 수와 관계없이 처리량이 약 4.4건/초로 유지됐습니다.  
현재 구조에서는 수신자 한 명의 발송이 끝나야 다음 수신자를 처리하기 때문에, 서버에 여유 자원이 있어도 여러 발송을 동시에 처리할 수 없습니다.

### 2) 외부 발송사의 지연을 그대로 받는다

발송사의 응답시간이 증가하면 전체 발송시간도 거의 같은 비율로 증가했습니다.  
외부 시스템의 일시적인 지연이 그대로 우리 서비스의 발송 지연으로 이어집니다.

### 3) 대량 발송이 다른 API까지 막을 수 있다

발송 요청 하나가 처리되는 동안 Tomcat 스레드 하나를 계속 사용합니다.  
동시 발송이 많아져 스레드가 모두 사용되면 발송과 관계없는 다른 요청까지 대기하게 됩니다.

### 4) 실패한 발송을 다시 처리할 방법이 없다

v1에서는 발송 실패 시 재시도하지 않고 바로 FAIL 상태로 저장합니다.  
모든 발송 시도가 끝나면 notification 상태가 COMPLETED가 되기 때문에 같은 요청을 다시 dispatch할 수도 없습니다.  
또한 발송 도중 서버가 종료되면 DISPATCHING 상태로 남게 되고, 이 상태 역시 다시 발송할 수 없습니다.  
즉, 실패하거나 중간에 중단된 작업을 이어서 처리할 방법이 없습니다.

## 6. v2에서 해결해야 할 것

v1 테스트 결과를 바탕으로 v2에서는 다음 문제를 해결하는 것을 목표로 잡았습니다.

1.  **실제 발송 작업을 API 요청 처리와 분리하는 것**입니다. 대량 발송이 진행되더라도 API 스레드가 발송이 끝날 때까지 점유되지 않아야 합니다.
2.  **여러 발송을 병렬로 처리할 수 있도록 만드는 것**입니다. 한 명씩 순차적으로 처리하는 구조에서 벗어나 처리량을 조절할 수 있어야 합니다.
3.  **실패한 발송을 재시도할 수 있도록 만드는 것**입니다. 일정 횟수 재시도한 뒤에도 실패한 메시지는 버리지 않고 별도로 보관할 필요가 있습니다.
4.  **서버나 Worker가 중간에 종료되더라도 작업을 이어서 처리할 수 있도록 만드는 것**입니다.
5.  **비동기 구조로 변경하면서 발송 지시가 유실되거나 같은 메시지가 중복 발송되는 문제도 고려**해야 합니다.

이 문제들을 해결하기 위해 v2에서는 Kafka를 이용해 API와 실제 발송 작업을 분리하고, 병렬 처리와 재시도, DLQ, 중단 후 재처리가 가능한 구조로 변경합니다.
